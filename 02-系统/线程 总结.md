终止线程

终止线程方法有四种：

- 线程 start 函数中 return
    
- 线程执行 pthread_exit： 不一定要在 start 函数中执行
    
- 其他线程发起 pthread_cancel
    
- 主线程 return，或者任意线程 exit()，导致进程终止，全部线程终止 --- 尽量不要这么做
    

  

主线程执行如下函数：

- return 或 exit：整个进程就结束了，所有线程都会退出
    
- pthread_exit : 主线程退出，其余线程继续
    

  

![](线程%20总结-20260911132020693-1.png)  

  

- retval ：其余线程可以通过 pthread_join 获得这个值，它必须存放在数据段或堆中
    

  

线程终止后回收资源

回收资源的目的：

- 防止成为僵尸线程，浪费资源
    
- 防止后续无法新建线程
    

  

回收线程资源：

- 谁来回收资源：any other thread in the same process
    
- 必须指定要回收的线程的线程 ID
    
- 这个函数不存在非阻塞调用。对于 not detached 的情况，如果线程未终止，会一直等待；如果线程已经终止，会马上返回
    

![](线程%20总结-20260911132020693-2.png)  

  

- thread: 要回收的线程 ID。
    
- retval：线程终止时的返回值，由 return 或 pthread_exit 产生

Detach Thread

目的：线程终止后，直接回收资源，没有必要告知其他线程自己的退出状态，可以 detach 实现更简单的处理。

  

![](线程%20总结-20260911132020695.png)  

  

- detach 之后，就不能通过 pthread_join 获取返回值了。
    
- detach 之后，如果任意线程 exit() 或者主线程 return，会导致进程终止，该线程也会终止
    

  

  

多进程和多线程的优劣比较：

- 多进程之间要采用 IPC 通信，因为彼此不共享信息
    
- 创建多进程相对 expensive。因为需要复制页表、把段标记改成只读、复制文件描述符表等
    
- 多线程之间，共享信息更容易。只要拷贝到数据段、堆就可以了
    
- 创建线程更快，因为不用做很多复制工作
    
- 线程之间，上下文切换更快，相比多进程。
    
- 多线程编程，必须要面对多线程安全问题，因为线程之间共享了数据，多进程基本就没这个问题
    
- 多线程编程，一个线程的 bug 可能影响到另一个线程，因为共享了数据
    
- 多线程，有独立的栈，会彼此竞争虚拟内存空间。虚存是有上限的，如果有很多线程或有多个虚拟内存很大的线程，就会出问题。多进程，每个都能达到虚存上限，会好很多。
    
- 多线程编程，最好不要使用信号
    
- 多线程编程，会共享文件描述符等资源，可能是优势，也可能是劣势。

线程 Cancel

线程 cancel 的场景：一个线程因为某种原因（比如出现某个错误），请求另一个线程终止

  

可以采用的另一办法是：设置一个全局的退出 flag，好处是更简单、更可控。

  

使用 cancle 的注意事项：

- 使用默认类型 PTHREAD_CANCEL_DEFERRED
    
- 设置 cancel 时的处理函数，完成回收资源等收尾工作
    

  

cancel 时线程退出过程：

- 执行 cancle 时设置的处理函数
    
- 释放 thread-specific-data
    
- terminate

其他

- 线程栈
    

每个线程都有自己的线程栈，大小是创建时就确定的。主线程线程栈会大一些，其余会小一些。在 X86/32，一般大约是 2M；在64位机器上会更高比如32M。

  

为什么要修改线程栈大小？

可能需要支持更多的自动变量，可能要支持更深的函数调用等等。

  

pthread_attr_setstacksize(): 在创建时，设置线程栈大小属性

  

另外，还有一个栈的大小限制 RLIMIT_STACK 。在 NPTL 线程模型下，这个值要求在程序启动前设置。

  

- 在线程中执行 exec(), fork(), exit()
    

线程中执行 exit，所有线程全部消失。no thread-specific data destructors or cleanup handlers are

executed

  

线程中执行 exec(),  程序会被替换，全部线程（除了调用exec的）都会消失，剩下的那个线程ID不确定。线程消失时，no thread-specific data destructors or cleanup handlers are executed

  

线程执行 fork()， 一般是不这么做的，通常推荐的是在 fork 后紧跟 exec

  

- 多线程场景下，信号是面向线程的，还是面向进程的
    

信号可以递送到进程，这时就是从所有没有屏蔽该信号的线程中选一个来处理这个信号。

信号也可以递送到某个线程。

  

如下情况下，信号递送到某个线程：

1. 线程写一个 broken pipe，引起 SIGPIPE
    
2. 线程引起硬件异常，如：SIGBUS, SIGFPE, SIGILL, and SIGSEGV
    
3. 同一进程中的某个线程发送信号给另一个线程，pthread_kill(), pthread_sigqueue()
    

  

信号掩码是线程层面的，每个信号可以不同，pthread_sigmask()。

  

信号的行为是进程层面的，也就是说：哪个线程执行是不确定的，但是表现出来是这个进程处理的。

1. 如果没有自定义处理函数，而是采用忽略、终止、停止、继续，那么信号会递送到某个没有屏蔽的线程处理。对于忽略，看上去就是整个进程忽略；对于终止，一个线程终止引起进程终止。
    
2. 如果自定义了处理函数，那么还是递送到某个没有屏蔽信号的线程，然后执行一次这个处理函数。
    

  

信号如果中断了 pthread_mutex_lock pthread_cond_wait , 会自动重启
